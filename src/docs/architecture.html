DigiSign architecture guide

How a PDF becomes a signed, checkable document: every step, which function runs, and what gets written where. Written from the code as it stands, not from the plans.

How to read this. Section 1 to 4 give you the vocabulary and the map. “The journey” walks one document from upload to verification, in order. “Deep dives” explain the three things that make the product trustworthy: the evidence, the manifest and the audit chain. Anything marked code points at a real file you can open.

1. What DigiSign is

A creator uploads a PDF, places fields (signature, date, text…) and names the people who must sign, in order. Each signer gets a link by email, opens it without an account, and signs. When the last person signs, the finished PDF carries a record that anyone can check on a public page.

Two promises are binding (PRODUCT.md):

  • Strict order. The next person is invited only after the previous one has signed. At most one signer per document is “invited” at a time.
  • Checkable file. The finished PDF contains its own record. A stranger can drop it on /verify and learn whether it is genuine and unchanged.
The one-sentence architecture: the browser reads, draws and stamps PDFs; the server is the evidence authority that stores facts, signs the final record and keeps a tamper-evident log. The server never parses or renders PDFs (the Cloudflare Worker is small and free-tier; PDF libraries only load in the browser).

2. Glossary

These words appear everywhere. Read once, refer back.

Document
One PDF being signed, plus its signers, fields and history. Row in documents. Statuses: draft, in_progress, completed, declined, voided, expired.
Signer
A named person on a document, with an email and a position in the order. Row in signers. They never have an account.
Field / layout
A box on a page that a signer fills: signature, initials, date signed, full name, text, checkbox. The layout is the full list of fields, saved as one JSON blob with a version number. Positions are in micro units: integers from 0 to 1,000,000 across the page (so they do not depend on screen size).
Geometry
Page sizes and rotation of the original PDF (mediaBox, cropBox, rotate), recorded at upload so fields can be placed and the PDF re-drawn identically later.
SHA-256 (a “hash”)
A fingerprint of some bytes: 64 hex characters. Change one byte and the fingerprint changes completely. Used to prove “this is exactly that”.
Canonical JSON
JSON written one single way (keys sorted, no spaces) so the same data always gives the same bytes, and therefore the same hash. code src/core/canonical-json.ts
Evidence
One signer’s private proof of signing: what they entered, when, their email, IP address, browser string, and when they consented. Stored as a JSON file in R2 and referenced by its hash. Private: never shown publicly. See Evidence.
Manifest
The public, signed summary of a completed document: source file hash, layout, every signer’s values, and the head of the audit chain. The server signs it with its private key and stores it in D1. The exact same signed bytes are embedded in the final PDF. See Manifest.
Audit chain
An append-only log per document where each entry contains the hash of the previous one, so editing or deleting any entry breaks every entry after it. Table audit_events. See Audit chain.
Ed25519
The digital-signature algorithm used to sign manifests. The server holds the private key (secret MANIFEST_SIGNING_KEY); the public key is published at /.well-known/digisign-keys.json, so anyone can verify.
Magic link
The signing URL /s/<token> emailed to a signer. The token is 32 random bytes; only its SHA-256 is stored, so a database leak cannot be used to sign.
Session
What the signer gets when they click “Review and sign”: a cookie digisign_signer (2 hours absolute, 30 minutes idle). Opening the link alone does not create one.
State hash
A fingerprint of everything a signer is agreeing to (source PDF + geometry + layout + the evidence of earlier signers). The browser sends it back when signing; if the document changed meanwhile, signing is refused.
D1
Cloudflare’s SQLite database. Holds all rows and the audit chain.
R2
Cloudflare’s object storage (like S3). Holds blobs: the original PDFs, evidence files, and anchored copies. “Blob” just means “a file of bytes stored under a key”.
Queue
Cloudflare Queues (ds-events): a to-do list for background work such as “send this email”. ds-dlq is the dead-letter queue for work that kept failing.
Outbox
A table of events written in the same database transaction as the change that caused them. A publisher then moves them to the Queue. This guarantees “the change happened” and “the follow-up work is queued” can never disagree.
Inbox
A table of events already handled, so a repeated delivery is ignored.
Idempotency key
A unique id the browser attaches to a request, so retrying the same request (flaky network) does not do the work twice. Table idempotency_keys.
CAS (compare-and-set)
“Update this row only if its version is still what I read.” Prevents two people overwriting each other. See Reliability.
Anchor
After completion, a copy of the manifest and a signed checkpoint of the audit head are written to R2 under keys that are never overwritten. See the honest note in Known gaps.
Sweeper
A cron job (every minute) that repairs lost work, expires old documents, sends one reminder, and cleans up.

The journey, step by step

Legend: Browser Server function / route Queue or cron Storage

  1. 1. Creator signs up or signs in

    Browsersrc/features/auth/auth-form.tsx → better-auth client. Serversrc/routes/api/auth/$.ts → getAuth() in src/lib/auth.ts (email + password, own hashing in server/password.ts).

    Writes: D1 user, account, session. Every owner action later calls resolveActor() (server/actor.ts) which turns the session cookie into the owner id.

  2. 2. Creator picks a PDF: draft and upload

    BrowserinitUpload() in features/editor/draft.ts:

    1. readUpload() reads the file, computes its SHA-256, counts pages and records each page’s geometry. The file does not leave the browser yet.
    2. ServercreateDraftFn → createDraft(): inserts the documents row (status draft, upload_status: pending) and audit entry #1 document.created, in one batch.
    3. initUploadFn → initUpload(): records expected hash, size, page count and geometry (a guarded update with a version check). This is a promise: “the file I am about to send has this fingerprint”.
    4. PUT /files/documents/:id/source → putDocumentSource() (domain/source.ts): checks the declared size matches, inserts a blob_intents row, then env.STORAGE.put(key, body, { sha256 }). R2 itself rejects the upload if the bytes do not match the promised hash. Then it reads the first 1 KB to confirm it starts with %PDF, and marks the document uploaded (plus audit #2 document.source_uploaded).

    Writes: D1 documents, audit_events (2 rows), blob_intents. R2 docs/<id>/<sha>.pdf.

    Why hash first? The server never trusts the browser’s claim about the PDF. The hash was promised before the bytes arrived, R2 verifies it, and the same hash later appears in the manifest. Everything downstream is anchored to “these exact bytes”.

  3. 3. Creator places fields and names signers

    BrowserThe editor (features/editor) keeps state locally and autosaves. ServersavePreparationFn → savePreparation() (domain/documents.ts) validates with zod (core/contracts, core/signer-rules.ts), then in one guarded batch rewrites the signers rows (order 1…n) and stores the layout as canonical JSON with layout_version + 1 and its hash.

    // one entry of layout.fields
{ "id":"01M49…", "signerId":"01M49…", "pageIndex":0, "kind":"signature",
  "x":694921, "y":745585, "w":184793, "h":45931, "required":true }   // micro units, 0..1,000,000

    Writes: D1 signers, documents.layout_json / layout_sha256 / layout_version. No audit entry yet (nothing is binding until publish).

  4. 4. Creator clicks Send: publish

    ServerpublishFn → publish(). It first runs publishBlocker() (domain/publish-rules.ts): upload finished, at least one signer, every signer has an email and a required signature, no field outside the page… Then one atomic batch:

    • CAS update: documents.status = 'in_progress', expires_at = now + 30 days, version + 1 (only if still draft and at the same version).
    • Audit entry document.published with the source, geometry and layout hashes. This freezes what is being signed.
    • Outbox row dispatch_next.

    Right after the commit, publishOutboxQuietly() pushes the outbox row onto the Queue (the “fast path”). If that push fails, the request still succeeds; the cron picks the row up within a minute.

    Writes: D1 documents, audit_events, outbox. Queue ds-events.

  5. 5. Background: invite the first signer and send the email

    Queuequeue() in server-entry.ts → handleEventBatch (engine/consumer.ts) → processEvent (engine/handlers.ts). Each message is only {eventId, type, documentId}; the handler loads the real payload from outbox.

    (a) dispatch_next → inviteNextSigner() (domain/invite.ts). It finds the first signer who has not signed; if that signer is pending and nobody earlier is unsigned, one batch does:

    • signer pending → invited (CAS),
    • new signer_tokens row holding only the hash of a fresh random token, expiring in 14 days,
    • audit signer.invited (stores a hash of the email, not the email),
    • outbox send_email whose payload temporarily contains the raw token.

    (b) send_email → sendEmail(): claims an email_deliveries row (so two workers cannot both send), builds the link <origin>/s/<token>, renders the HTML + text with renderEmail() (server/mail/templates.ts), sends through getMailer() (server/mail/index.ts: SMTP if configured, else Resend, else console), marks the delivery sent, and scrubs the raw token out of the outbox row. After that, nobody (not even the database) can reconstruct the link.

    Writes: D1 signers, signer_tokens, audit_events, outbox, email_deliveries, inbox. No R2.

  6. 6. Signer opens the link

    Browser/s/$token → ServerpeekInviteFn → peekInvite(). This is read-only: it hashes the token, looks it up, and returns a minimal summary (document title, sender, how many fields, or a reason such as expired / replaced / cancelled). Opening the link records nothing and signs nothing.

    Clicking Review and sign → exchangeSignerTokenFn → exchangeSignerToken(): inserts a signer_sessions row (hash of a new random id) and sets the digisign_signer cookie. The token is not consumed; it stays valid for 14 days so a signer can come back.

    The desk (/sign) calls getSigningContextFn → openSession() + buildView(). The first time, markViewed() sets first_viewed_at and writes audit signer.viewed. The PDF itself is fetched from GET /files/documents/:id/source using the cookie (readDocumentSource() checks that the session’s signer belongs to this document).

    Writes: D1 signer_sessions, signers.first_viewed_at, audit_events. R2 is only read.

  7. 7. Signer signs

    Browserfeatures/sign/signing-desk.tsx: the signer fills fields; a signature is either drawn (strokes packed into a compact base64 string, core/strokes-codec.ts) or typed (name + font). Entries are kept in sessionStorage so a refresh loses nothing. On confirm, the browser sends { idempotencyKey, stateHash, consent: true, values[] }.

    ServersubmitSignatureFn → submitSignature() (domain/signing.ts), in this order:

    1. Replay check: same idempotency key + same request hash → return the saved answer. Same key, different body → error.
    2. Authorization: session valid, document in_progress, signer invited.
    3. Completeness: all this signer’s required fields have answers (answerReady).
    4. State hash: recompute it from the stored document; mismatch → “This document changed”.
    5. Seal evidence: sealEvidence() builds the evidence object, canonicalises it, hashes it, and the server writes it to R2 (evidence/…) after a blob_intents row.
    6. One atomic batch (guardedBatch): signer → signed (with evidence key/hash, IP, user agent, consent time), document version bump, audit signer.signed, outbox event, idempotency row.

    Writes: R2 evidence/…json. D1 signers, documents, audit_events, outbox (dispatch_next), idempotency_keys, blob_intents.

    If this is not the last signer, the outbox row is dispatch_next and step 5 repeats for the next person. That loop is the “strict order” promise.

  8. 8. The last signer: completion

    In the same submitSignature() call, when everyone else has signed:

    1. buildCompletedManifest() gathers every signer’s evidence summary and builds the manifest, including audit.headSeq/headHash (the chain head after this signature).
    2. signManifest() canonicalises it, hashes it and signs it with Ed25519.
    3. The batch additionally sets documents.status = 'completed', stores manifest_json (the signed envelope) and manifest_sha256, writes audit document.completed, and inserts two outbox rows: anchor_manifest and notify_parties.

    Then in the background:

    • anchor_manifest → anchorManifest(): copies the manifest to R2 manifests/…, signs a checkpoint {documentId, seq, headHash, manifestSha256} and writes it to anchors/…, then sets documents.anchored_at.
    • notify_parties → notifyParties(): one send_email outbox row per recipient (owner + each invited signer) using the “completed” template with a link to /v/<documentId>.

    Writes: D1 (documents completed + manifest, 2 audit rows, 2+ outbox rows). R2 manifests/…, anchors/….

  9. 9. The signed PDF is built in the browser

    BrowserConfirmation screen and dashboard (features/sign/confirmation.tsx, features/dashboard/signed-pdf.ts) fetch the original PDF and call render() in src/pdf/render.ts with the manifest. It is deterministic: same inputs, same bytes. It:

    • draws every field value onto its page (drawn strokes, typed signature in an embedded script font, dates, text, check marks),
    • adds a footer to each original page: a hairline and one line, “Signed with DigiSign · <verify address>”,
    • appends a branded certificate of completion (one page for a normal document, more only for very long signer lists): title and facts, the signers in order with UTC times, a QR code with “Check this file”, and the three SHA-256 fingerprints,
    • sets the PDF Info key DigiSignDocumentId,
    • attaches digisign-manifest.json inside the PDF: the server’s signed envelope, byte for byte (documents.manifest_json, returned to the browser as record.envelope). The browser never rebuilds or edits it.

    That attachment makes the file self-describing and independently checkable: it names the document and carries the Ed25519 signature, so anyone with the public key can verify the manifest even without our server. The signer’s confirmation screen, the dashboard download and the verify page all draw the PDF from the same server record, so they all produce identical bytes.

    Renderer version. Because verification compares bytes, any change to the drawing code changes every PDF. The manifest records renderer.version (now 1.1.0, constants in src/core/renderer.ts; the design is in src/pdf/branded.ts). Nothing is published yet, so there is only one drawing path. Before the first real document is signed, decide the rule: from then on, never edit released drawing code. Add a new version and dispatch on manifest.renderer.version, so old documents keep verifying.

  10. 10. Anyone checks a PDF

    Browser/verify (features/verify). The file never leaves the browser until it is identified:

    1. identifyPdf() finds the document id: embedded manifest first, then the Info key, then the footer text.
    2. SerververifyManifestFn → verifyRecord() (domain/verify.ts) recomputes everything it can: the Ed25519 signature over the manifest, the manifest hash, the source hash, the whole audit chain (every hash, in order, ending at the head the manifest names), and that the original PDF still exists in R2. It also returns a 10-minute read grant for the original PDF.
    3. Browserfetches the original with the grant, re-renders the final PDF from original + manifest, and compares it to the file the person dropped.
    4. decideOutcome() (features/verify/outcome.ts) turns the results into one of seven verdicts: valid, modified, not-comparable, record-only, not-found, failed-checks, incomplete.

    Public audit rows contain hashes and times only; no emails, IPs or user agents.

Evidence (deep dive)

Evidence is the private proof of one person signing. It answers: who, when, from where, what exactly did they enter, and did they consent. It is private because it contains personal data.

// stored in R2 at evidence/<doc>/<signer>/<sha>.json  (canonical JSON)
{
  "documentId": "01M49…",  "signerId": "01M49…",
  "signedAt": 1791323229260,
  "values": [ { "fieldId":"…", "signature":{ "kind":"drawn", "box":{…}, "strokes":"CABb…" } },
              { "fieldId":"…", "text":"TYO" } ],
  "valuesSha256": "b3be2b…",                 // fingerprint of just the values
  "email": "…", "ip": "…", "userAgent": "…", // PRIVATE
  "consentAt": 1791323229260,
  "invitedAt": …, "firstViewedAt": …,
  "privateEvidenceSha256": "c0a83b…"         // fingerprint of the private part
}

How it connects to the public record. The file’s own SHA-256 is saved in signers.evidence_sha256 and in the audit entry signer.signed. The manifest does not contain the email or IP; it contains valuesSha256 and privateEvidenceSha256. That is a commitment: if a dispute ever arises, you can reveal the private evidence and anyone can check it hashes to the value already sealed in the signed manifest, without the public ever having seen it.

Evidence is written before the database commit. If the commit then fails, the R2 object is an orphan; the blob_intents row lets the sweeper delete it after a day.

Manifest (deep dive)

The manifest is the signed, public description of a finished document. Everything needed to redraw the PDF and to check it, nothing private.

// documents.manifest_json  =  the signed ENVELOPE
{
  "manifest": {
    "v": 1, "documentId": "01M49…", "title": "…",
    "source": { "sha256": "cc3ff8…", "size": 183204 },   // the original PDF
    "geometrySha256": "a9e76a…", "layoutSha256": "…",
    "geometry": [ { "mediaBox":[0,0,595.28,841.89], "cropBox":[…], "rotate":0 } ],
    "layout":   { "documentId":"…", "layoutVersion":3, "fields":[ … ] },
    "signers":  [ { "order":1, "signerId":"…", "name":"TYO", "signedAt":1791323229260,
                    "values":[ … ], "valuesSha256":"…", "privateEvidenceSha256":"…" } ],
    "completedAt": 1791323229260,
    "audit":    { "headSeq": 9, "headHash": "8a5a08…" },  // ties the manifest to the chain
    "renderer": { "name":"digisign-render", "version":"1.0.0" }
  },
  "keyId": "k1",
  "sig": "WE0fP80x3P…"     // Ed25519 signature over canonicalJson(manifest)
}

Where copies live: (1) D1 documents.manifest_json, the primary copy; (2) inside every downloaded PDF as digisign-manifest.json, the same signed bytes; (3) R2 manifests/… after anchoring.

What it proves. The signature proves DigiSign’s server produced exactly this manifest. The source.sha256 proves which original PDF it is about. audit.headHash proves which history it was built from. The renderer is deterministic, so original + manifest always produce the same final PDF bytes, and that is how a modified file is detected.

Audit chain (deep dive)

One row per event, per document, in audit_events, written in the same transaction as the change it describes.

seqtypeactorpayload (examples)
1document.createdowner{title}
2document.source_uploadedowner{sourceSha256}
3document.publishedowner{sourceSha256, geometrySha256, layoutSha256}
4signer.invitedsystem{signerId, order, emailSha256}
5signer.viewedsigner{signerId}
6signer.signedsigner{signerId, evidenceSha256, stateHash}
…repeat invited / viewed / signed for each signer
lastdocument.completedsystem{manifestSha256}
Other types: signer.declined, document.declined, document.voided, document.expired.

How the chain works. Each row’s hash is the SHA-256 of its own fields plus the previous row’s hash (planAudit() in domain/audit.ts):

genesis = sha256("digisign:genesis:" + documentId)        // the “row 0” hash
hash[n] = sha256( canonicalJson({ documentId, seq, type, actorType, actorId,
                                  occurredAt, payload, prevHash: hash[n-1] }) )

Change or delete row 5 and every later hash stops matching. verifyRecord() replays the whole chain and also requires that the manifest’s audit.headSeq/headHash exists in it.

The chain is tamper-evident, not tamper-proof: someone with full database write access could rewrite the whole chain consistently. The signed manifest and the R2 checkpoint raise the bar (they pin the head hash), and a future external timestamp would close the gap. See Known gaps.

Signing key

  • Algorithm: Ed25519 via Web Crypto (server/manifest-key.ts).
  • Private key: secret MANIFEST_SIGNING_KEY (base64 PKCS8). Key id is the constant k1 in code.
  • Public key: GET /.well-known/digisign-keys.json. Anyone can verify a manifest with it, independent of our server.
  • If the secret is missing, the code generates a random throw-away key labelled dev per server instance. Fine for local work; in production it would make old manifests unverifiable. It is set in production today.
  • Rotation: not built. A new key would need a new keyId and a list of old public keys.
  • The same secret also keys the HMAC for 10-minute read grants (domain/grants.ts).

Reliability patterns

The app runs on serverless pieces that can fail between any two steps. These patterns make “half done” impossible or repairable.

Security and privacy

ConcernWhat the code does
Stolen databaseMagic-link tokens and session ids are stored only as SHA-256 hashes. The raw token is scrubbed from the outbox after the email is sent.
Other signers’ privacyA signer’s browser never receives other signers’ emails, IPs or user agents. They see only names and statuses.
Public dataThe public audit view and manifest hold names, values, hashes and times. Emails appear only as hashes; IPs and user agents only inside private evidence.
Decline reasonEmailed to the document owner only, never to other signers.
Link replayOpening a link records nothing and does not consume it. A session (2 h, 30 min idle) is required to view or sign. A re-issued link revokes the old one.
Wrong-time signingThe state hash blocks signing if the document changed; status and CAS checks block double signing.
Cross-site requestscrossSiteRejection() in server/security.ts; security headers on every response.
Who can read the PDFThe owner; a signer with a valid session on that document; or anyone with a 10-minute HMAC grant, issued only for completed documents.
InputEvery server function validates with zod (strictObject, size and count limits).
Not built yet: rate limiting, a signer one-time code (email OTP) on top of the link, email verification and password reset for creators. A link is a bearer credential: whoever holds it can sign as that person.

Decisions and why

PDF work in the browser, not the Worker
Workers have a size and CPU budget; pdf.js, pdf-lib and fonts are large. The server never opens a PDF. pnpm check:bundle fails the build if those libraries leak into the Worker bundle. Browser-only screens load through lazyDesk().
Server stores facts, browser draws the result
The final PDF is not stored; it is regenerated deterministically. Less storage, and verification works by re-rendering and comparing.
Hash the file before uploading
The server learns the expected fingerprint first, R2 enforces it, and the manifest repeats it: one chain of “this exact file”.
Canonical JSON everywhere
Hashes and signatures only work if both sides serialise identically. One implementation in core.
Content-addressed R2 keys
The key includes the hash, so objects are immutable in practice and safe to write twice.
D1 for facts, R2 for blobs
Small, queryable, transactional data in SQLite; larger or private files in object storage.
Outbox + Queue + cron instead of “do it in the request”
Sending email must never block or break a signature. State and event commit together; delivery can retry independently.
Strict sequential invite
Enforced in inviteNextSigner() by order, status and CAS, and re-triggered by each signature’s dispatch_next. Not just a UI rule.
Evidence separated from manifest
Public verifiability without publishing personal data, with a hash commitment that allows later disclosure.
No accounts for signers
Lower friction. The trade-off is that the link is the credential, which is why the session window is short and links can be replaced.
Dates in UTC
“Date signed” is the server time in UTC, shown with the zone, so it never depends on a signer’s device clock.

Known gaps and open decisions

  • “Anchored” is a copy in our own R2, not an outside timestamp. The checkpoint is signed by our key and never overwritten, but a third party (an RFC 3161 timestamp authority, a transparency log) would be needed to prove the record existed at a time without trusting us. The UI wording (“Timestamp anchoring: Complete / In progress”) should be confirmed against this.
  • Legal text. The “How electronic signing works” dialog shows a placeholder (TODO(legal)) and the consent wording needs legal review.
  • Personal data at rest. Signer emails sit in plain text in D1 and in evidence files; IP and user agent are stored per signature. A retention policy is not defined.
  • Signing key rotation and revocation are not implemented (single k1).
  • Link is a bearer credential; no second factor and no rate limits yet.
  • Email deliverability: Gmail SMTP is a stop-gap (about 500 recipients a day). A verified domain with Resend is the long-term path.
  • Non-Latin text in the PDF. Field text and the certificate use built-in PDF fonts that only cover Western European characters. A value in another script (for example Bengali or Chinese) no longer breaks the PDF, but each character the font cannot draw is shown as “?”. Real support needs a bundled Unicode font (a subset of Noto Sans per script), which is a size and licensing decision.
  • Production configuration items listed under “Config and deploy” are unresolved.
